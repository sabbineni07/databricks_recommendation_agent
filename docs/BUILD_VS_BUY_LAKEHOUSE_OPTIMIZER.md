# Build vs Buy: In-House AI Agents Framework vs Blueprint Lakehouse Optimizer (LHO)

This document compares your in-house Databricks AI Agents framework with **Blueprint Lakehouse Optimizer (LHO)** and provides a point of view on build vs buy. It is based on your vision docs and LHO’s public documentation ([Introduction](https://blueprinttechnologies.atlassian.net/wiki/spaces/BLMPD/pages/2629042214/Introduction), [Unifying the Lakehouse](https://blueprinttechnologies.atlassian.net/wiki/spaces/BLMPD/pages/3724705806/Unifying+the+Lakehouse+Consolidation+Serverless+Acceleration+and+Governance+for+Databricks+at+Scale), [Cost & Performance Optimization](https://blueprinttechnologies.atlassian.net/wiki/spaces/BLMPD/pages/3734044680/Cost+Performance+Optimization+intro)).

---

## 1. What Each Solution Is

### Your framework (in-house)

- **Multi-agent AI platform** for the full data engineering lifecycle (Design → Build → Run → Monitor).
- **Six agents (planned):** Cluster Recommender ✅, Job Log Analyzer, Failure RCA, Pipeline Agent (STTM→code), Semantic Data Type, Data Quality.
- **Tech:** LLM-powered (e.g. Azure OpenAI / GPT-4o), RAG (Azure AI Search), LangGraph, shared API and patterns. Recommendations and explanations are **generated by LLMs** from metrics, patterns, and (planned) pipeline/data-volume context.
- **Value:** Cost savings (20–40% cluster), MTTR reduction (~80%), faster pipeline build (30–50%), governance and data quality; **one platform, many agents**, extensible to new use cases.

### Blueprint Lakehouse Optimizer (LHO)

- **Unified optimization and observability platform** for Databricks: cost governance, performance optimization, visibility across compute, storage, pipelines, vendors, and governance.
- **Core capabilities (from LHO docs):**
  - **High-resolution compute telemetry** (e.g. every 5–10 seconds).
  - **Contextual KPIs:** cost per TB, cost per task, data I/O, CPU/memory saturation.
  - **Optimization insights:** “Why did cost change?”, “What changed in job behavior?”.
  - **Anomaly detection** for cost, performance, and usage.
  - **Forecast modeling** for spend and commit utilization.
  - **Usage distribution analysis** (e.g. percentile-based CPU/memory).
  - **Cross-workspace visibility** (multi-region, multi-team).
  - **Governance automation:** policies, alerts, incident rules.
  - **Themes:** workspace consolidation, serverless recommendations, UC migration assessment, multi-tenancy.
- **Positioning:** “Deep visibility, predictive analytics, and automated optimization insights based on **real workload behavior—not superficial cluster metrics**.” Focus on **telemetry, analytics, and governance**, not on LLM-generated narrative or code/spec-to-pipeline generation.

## 2. Overlap: Does LHO Cover Your Use Cases?

| Your use case | LHO coverage | Overlap / gap |
|---------------|--------------|----------------|
| **Cluster Resource Recommender** | Strong overlap. LHO provides cost/performance optimization, optimization insights, and (with serverless) recommendations. | **Overlap:** Right-sizing, cost visibility, “why did cost change?”. **Difference:** Yours is **LLM + RAG** (natural-language rationale, pattern matching from historical recommendations); LHO is **rules/analytics-driven** with rich telemetry. LHO may give **better raw data** (5–10 s telemetry, KPIs); yours gives **explainable, narrative recommendations** and can ingest pipeline/data-volume context later. |
| **Job Cluster Log Analyzer** | Partial. LHO has telemetry, insights, and anomaly detection. | **Overlap:** Understanding job behavior, spikes, anomalies. **Gap:** Your agent is explicitly **Spark plans + cluster logs → LLM analysis** (bottlenecks, skew). LHO does not present as an “analyze this Spark plan / log” conversational or document-level analyzer. |
| **Job Failure RCA Agent** | Partial. LHO has “optimization insights,” anomaly detection, and incident/alerts. | **Overlap:** Anomaly and “what changed?” support diagnosis. **Gap:** Your RCA is **LLM-driven root cause + remediation** (narrative, suggested fixes). LHO is not described as an RCA agent that produces causal narrative and action items from failure events. |
| **Data Engineering Pipeline Agent** | No. | **Gap:** You plan **STTM/specs → pipeline code**. LHO focuses on cost, performance, and governance of existing workloads, not generating pipelines from documentation. |
| **Semantic Data Type Agent** | No. | **Gap:** You plan **infer and tag semantic types** (PII, currency, dates). LHO does not describe semantic classification or data-asset tagging. |
| **Data Quality Checks Agent** | No (or minimal). | **Gap:** You plan **auto-generate and run DQ checks**. LHO’s governance is about cost/policy/usage, not data quality rules and execution. |

**Summary:** LHO **strongly overlaps** with **cost/performance optimization and observability** (and extends into consolidation, serverless, UC, multi-tenancy). It **does not** cover **pipeline generation**, **semantic data typing**, or **data quality agents**, and it is not positioned as an **LLM-based RCA or log analyzer**.

## 3. Build vs Buy: Considerations

| Factor | In-house framework | Blueprint LHO |
|--------|--------------------|---------------|
| **Cost/performance optimization** | You build and own it; depth depends on telemetry you ingest (e.g. Delta table today). | Purpose-built; high-resolution telemetry and KPIs out of the box; likely **faster time-to-value** for cost/observability. |
| **LLM-driven recommendations & explanation** | Core design: narrative rationale, RAG over historical patterns, extensible prompts. | Not the main product; LHO is analytics and governance, not “ask the lakehouse” or generated explanations. |
| **Pipeline / Semantic / DQ agents** | In your roadmap; no equivalent in LHO docs. | Not in scope for LHO. |
| **Failure RCA & log analysis** | LLM-based RCA and log/plan analysis in scope. | Anomaly and insights help, but not an RCA “agent” or log-level LLM analysis. |
| **Control and roadmap** | Full control; align agents to internal STTM, data quality, and tooling. | Roadmap and features set by Blueprint; less say in “agent” shape and LLM use. |
| **Total cost of ownership** | Build and run (eng, infra, LLM, RAG); ongoing iteration. | License + implementation; less build, but recurring cost and vendor dependency. |
| **Strategic differentiation** | AI-assisted data engineering as a **platform** (many agents, one stack). | Optimizer as a **product**; strong on cost/governance, not on generative agents. |

## 4. Point of View and Options

### LHO does **not** fully replace your vision

- **It covers:** Cost and performance optimization, visibility, forecasting, governance, serverless/consolidation/UC/multi-tenancy—i.e. the **“Monitor & Optimize” and “Run”** space, especially **cost and observability**.
- **It does not cover:** Pipeline-from-STTM, semantic data typing, data quality agents, or **LLM-native** RCA and log analysis. So **build vs buy** is not “all or nothing”; it’s **where to use a product vs where to build**.

### Recommended direction: **hybrid, use-case-by-use-case**

1. **Cost/observability foundation (consider LHO)**  
   - Use LHO (or a similar product) for **high-resolution telemetry, KPIs, forecasting, and governance** if:
     - You need **faster** visibility and cost control than building telemetry and dashboards in-house.
     - You care about **commit utilization, cross-workspace, and policy automation**.
   - Then your **Cluster Recommender** can consume **LHO-derived or LHO-complementary metrics** (and later pipeline/data-volume context) and still provide **LLM-generated recommendations and explanations**. So: LHO = “better data and governance”; your agent = “better narrative and right-sizing logic” that can sit on top of that data.

2. **Keep building: LLM agents LHO doesn’t offer**  
   - **Failure RCA, Log Analyzer, Pipeline Agent, Semantic Data Type, Data Quality** are **not** in LHO’s scope. If those are strategic, they remain **in-house (or partner-built)** on your framework.

3. **Cluster Recommender: enhance, don’t necessarily replace**  
   - If you adopt LHO, treat it as the **telemetry and cost-insight layer**; keep or refine your **Cluster Recommender** to:
     - Ingest **richer metrics** (from LHO or from your Delta table that LHO might feed).
     - Add **pipeline code and data volume** (per your plan) and **RAG** over historical patterns.
     - Produce **LLM-generated rationale and recommendations** that LHO does not provide in the same form.

4. **Decide based on priorities**  
   - **If “cost visibility and governance fast” is the top priority** → Pilot LHO; use it for telemetry and cost; keep your recommender (and future agents) as the LLM layer.  
   - **If “full control and no vendor for cost/observability” is the priority** → Continue building; consider improving your own telemetry (e.g. 5–10 s granularity, KPIs) and treat LHO as a benchmark.  
   - **If “pipeline, semantic, DQ, and RCA are the main differentiators”** → Build those regardless; LHO does not substitute for them.

## 6. Next Steps (suggested)

1. **Discovery with Blueprint:** Request a **detailed capability matrix** (APIs, export of metrics/insights, integration points) so you can assess whether LHO can **feed** your Cluster Recommender and future agents (e.g. via API or warehouse).
2. **Clarify roadmap:** Confirm which use cases are **must-have in 12–18 months** (e.g. RCA, pipeline agent, DQ). That drives “build these regardless of LHO.”
3. **Pilot scope:** If trialling LHO, define a **pilot** (e.g. one workspace, cost + one optimization workflow) and in parallel keep **one in-house agent** (e.g. Cluster Recommender) consuming the same or complementary metrics to compare **recommendation quality and explainability**.
4. **Document integration:** If you adopt LHO, add a short “LHO integration” note to your architecture: how LHO fits (telemetry/governance) and how your agents consume its outputs (e.g. `docs/PLAN_PIPELINE_AND_DATA_VOLUME_CONTEXT.md`, data sources section).
